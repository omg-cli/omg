# v0.1.225 beta release

This release brings the accumulated package, runtime, daemon and verification changes since v0.1.224 into one published version. The [complete comparison](https://github.com/omg-cli/omg/compare/v0.1.224...v0.1.225) includes the individual fixes and verification records.

## Security changes

- Native Arch/AUR admission displays disclosed affected-version and watch-list findings with advisory links. Installing them requires a foreground terminal's exact `accept <review-id>` answer. Generic `--yes`, blank input, EOF, signals and unattended execution cannot accept that risk. Approval binds the prepared transaction, principal, policy and artifact bytes; it does not override source, license, signature or archive requirements.
- Managed npm tools resolve an exact, bounded dependency lock before materializing packages or running lifecycle scripts. OMG checks every distinct direct/transitive registry version through OSV, requires separate consent for findings, rechecks evidence and policy through publication and rejects changed lockfiles or runtime binaries. Frozen installation retains signature verification and separately scoped script permission. Failures preserve an existing working tool.
- Managed Cargo, Go and Python tools review resolved direct and transitive public-registry versions before building or installing. Cargo binds crates.io checksums and its frozen dependency graph; Go binds module identities and checksums before an offline build; Python reviews bootstrap packages and wheel hashes before an offline, binary-only installation. Each path retains the selected managed runtime and rechecks the reviewed artifacts through publication. Failed installation preserves the previous tool.
- APT and DNF review their proposed transactions before installation. APT retains its native cache and package lock through commit; DNF binds a private stored transaction and its RPM artifacts before strict replay. Homebrew and native sources without a complete, authenticated mapping require explicit Unknown-risk consent. Generic `--yes` cannot accept these coverage gaps.
- Managed runtime installation and selection check vendor advisory evidence before candidate execution, publication and activation. The 13 runtimes are Node, Python, Go, Rust, Ruby, Java, Bun, Deno, Zig, .NET, Erlang, PHP and Swift. Missing mappings, stale evidence, provider failures and unresolved integrity changes require explicit Unknown-risk consent. Acceptance binds the runtime bytes, publisher metadata, policy, principal and evidence; verified replacement is required to clear an integrity gap.
- Pi is an npm-installed coding harness. Its installer uses the shared npm dependency, CVE, signature and managed-Node checks. It no longer uses ambient npm.
- `omg new` generates React, Node, Rust, Python and Go templates locally. React and Node declare dependencies in `package.json` for later review. Scaffolding uses Git to initialize the repository and reads the selected runtime version from OMG state.
- `omg container build` identifies OMG-generated recipes and asks for transaction-specific consent when advisory coverage is Unknown. The build uses the reviewed recipe and ignore rules. Explicit OMG package policies that require an enforceable transaction stop the build before the engine starts.
- Automatic runtime PATH selection consumes valid cached admission without fetching or prompting. Tasks retain runtime use leases through execution; parallel readers can coexist while mutation remains excluded. Automatic virtualenv activation verifies the base Python, and missing package managers must use reviewed tool installation instead of ambient corepack bootstrap.
- Node downloads authenticate the signed checksum manifest against pinned active Node releaser certificates before selecting the archive digest. Unknown, expired, revoked and invalid signers are refused. There is no unsigned fallback or personal keyring mutation. Builds without PGP support refuse new Node downloads.
- Swift signing keys use bounded HTTP metadata decoding while retaining pinned fingerprint validation. SDK archives and signatures retain their byte-preserving download path. Swift installs support larger vendor-signed SDKs with a 4 GiB expansion limit applied after pinned signature verification. Other gzip runtime archives retain their 2 GiB default.
- Arch/AUR transaction, private staging/build, elevation, provenance, cancellation and Omarchy migration boundaries receive the accumulated hardening in this release. The ALPM dependency family is pinned to an immutable upstream commit.
- On Omarchy, `omg update` coordinates snapshots, repository and AUR upgrades, migrations, service restarts, hooks and boot verification. It reads the configured repositories and runs the vendor Git-only update step for a linked Omarchy checkout. Nested lifecycle commands resolve from the packaged runtime. A cache-prune failure or an unavailable AUR produces a warning and lets the remaining checks run. Package operations and AUR admission stay in OMG.

## Advisory service

The deployed Cloudflare service provides an indexed rolling 30-day view of stored CVE revisions, retained older records, Arch advisories and CISA KEV annotations. Public responses use bounded caching and ETags. FIRST EPSS enrichment supplies dated probability/percentile values and up to 30 days of available history for imported CVEs. Genuine zero, missing scores, stale scores and provider failures remain distinct; failed refreshes retain previous history without asserting a current score.

The release gate requires a complete CVE baseline authenticated against the publisher's archive and Git identities, followed by a fresh delta checkpoint. Import progress alone cannot certify completeness. Missing records and unsupported package mappings remain Unknown. EPSS is prioritization context, not proof of safety or current exploitation. Zero Wire content is not redistributed without verified permission. Public feeds cannot establish the absence of undisclosed zero-days.

Vendor assessments use fixed primary sources, bounded parsers and private D1/R2 snapshots. A scheduled GitHub Actions refresh uses an ephemeral read-only job token to avoid shared unauthenticated GitHub API quotas. Public rechecks keep original timestamps when reusing fresh evidence. Forced checks near expiry revalidate upstream and renew timestamps only after success. Ruby requirements use a Ruby comparator, including four-component historical versions; .NET SDKs are mapped to their actual runtime/ASP.NET components before CVE comparison.

## Native packages, runtimes and daemon

This release includes the intervening Arch, Debian/Ubuntu and Fedora package/daemon fixes, runtime and environment ownership/restore fixes, bounded process lifecycle work, and stricter real QEMU acceptance. Linux archives distinguish Debian Bookworm's APT 6 ABI from Debian Trixie's APT 7 ABI. OMG and omgd remain a matched release pair; restart an already running daemon after updating.

## Upgrade notes and coverage limits

- Managed npm tools now require an active OMG-managed Node with bundled npm >=11.15.0. Use a current supported Node release. Ambient npm, private registries, registry aliases and non-registry resolver sources are not accepted by this gate. Existing Windows NVM/Node/npm installations are not migrated.
- npm lifecycle scripts remain disabled unless separately allowed for that exact package. CVE acceptance does not grant script or unverified-signature permission.
- Attended risk consent uses foreground terminal ownership checks on Linux and macOS. Generic `--yes` cannot acknowledge advisory risk or missing coverage. Arch's default `optional` policy now requires explicit Unknown-coverage consent when the advisory feed is unavailable; unattended offline installs refuse.
- Prepared native transaction consent applies to Arch/AUR, APT and DNF. DNF's installed-package advisory interface does not establish complete coverage for newly proposed packages; Homebrew lacks a frozen complete transaction interface, and local Debian files can have unresolved dependencies. These paths disclose Unknown coverage rather than claiming a clean result. Runtime source coverage can remain partial, including bundled components and unsupported publisher mappings.
- Cargo, Go and Python tool installation requires the corresponding OMG-managed runtime. Nonpublic or unresolved dependencies require explicit coverage-gap consent; unsupported sources and changes to frozen artifacts can still prevent installation. Python tool installation accepts wheels only; source distributions are not built by this path.
- Older Node releases signed only by excluded historical authorities may be refused. Existing installations without authenticated publisher records remain Unknown even when their declared version appears unaffected.
- Existing runtime admission expires after 30 minutes and is rechecked against installed content, identity, policy and principal. Large runtime trees require disk reads; this release does not promise instant shell-hook execution.
- Bare runtime commands in tasks require a reviewed managed installation, including after task environment overrides. Existing external rustup/system installations do not establish OMG advisory authority. Virtualenvs retain their own site-packages with a reviewed base Python; recreate them when their base differs.
- Windows testing uses WSL and the Linux build. This release does not introduce a native Windows package backend.

## Release provenance and project maintenance

The release pipeline requires exact-commit CI, security, coverage, benchmark and native acceptance before publication. It collects six platform archives with checksums, includes a locked CycloneDX SBOM, generates GitHub/Sigstore build provenance and attaches `omg-release.sigstore.json`. Verify downloads against the source tag and release workflow, as described in the generated release instructions. R2 publishes the latest-version marker only after archive/checksum round-trip verification.

GitHub Sponsors links the maintainer's existing public profile. The repository now includes Contributor Covenant 2.0, maintainer-led governance and OpenSSF Scorecard publication alongside the existing security reporting policy. Grant or fiscal-host acceptance is not implied by these files.
