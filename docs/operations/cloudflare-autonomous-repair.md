# OMG cloud repair operation

This document describes the repair paths added after the original Cloudflare CI adaptation. Source implementation, deployed configuration, and end-to-end acceptance are separate gates. An installed GitHub App or a passing unit suite does not establish a working unattended repair.

## Cloud model and required skills

Cloud inference uses Workers AI model `@cf/deepseek-ai/deepseek-v4.1-flash-1017`. The coding harness selects low reasoning. Local Codex model settings do not configure Cloudflare. The model is documented in the [Workers AI catalog](https://developers.cloudflare.com/workers-ai/models/deepseek-v4.1-flash-1017/). Coding keeps its existing 6,000 output-token limit and 16 agent steps; diagnosis keeps its 24,000 output-token limit. The controller verifies the same reasoning configuration reported by the coder.

Coder and inspector share the OMG `ModelPacer` Durable Object. It admits at most one inference every 12 seconds. CodeLoud's separate pacer permits 15 requests per minute on the same account and model, leaving five of the documented [20 requests per minute for paid Workers AI models](https://developers.cloudflare.com/workers-ai/platform/limits/) for OMG. Other callers can still consume that shared account quota. Provider failures remain terminal under the existing retry policy. Admission waits obey the caller's cancellation signal and never authorize another inference attempt.

The pinned coding bundle includes Potato Mode, Ponytail, Rust best practices, Rust async patterns, and TDD. Bundle validation checks every source file hash. Mandatory guidance is delivered again when OpenCode generates or compacts context. A changed bundle requires a coder deployment and matching trusted bundle pin before a new operation starts.

## Source review and runtime leads

The weekly source review inventories one immutable main tree. Bounded pages distinguish source supplied to the model, source actually read, and files held for an unsupported type or size. A continuation uses the previous private review record and the same tree identity. If main advances, the old snapshot is incomplete; it is not credited as a complete review of the new tree.

GitHub's default concurrency queue retains only one pending run and replaces it when another arrives. Weekly continuation and runtime polling must not silently replace each other. GitHub documents `queue: max` for up to 100 pending runs with cancellation disabled. Queue capacity remains finite. See [workflow concurrency](https://docs.github.com/en/enterprise-cloud@latest/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency).

The standalone Cloudflare verification and AI review workflows share `omg-ai-review-global`. Each full CI run uses two parallel Sandbox checks, so the shared queue serializes these GitHub runs against the two configured container slots. It does not lease capacity for direct API callers or backend work that survives a GitHub timeout.

Runtime polling first checks the private Sentry queue. An empty queue starts no native checks or inference. Sentry evidence identifies the observed release separately from the current source snapshot. An older or unknown event source SHA is a historical lead, not proof of a current defect.

A runtime incident reserves its review owner before source inspection. If publication fails after verification, later polling replays the original durable result and proof identities. It cannot replace that work with a new no-findings result. A claim without a durable record can be recovered only after a definite record-not-found response and independent confirmation that the exact original GitHub attempt completed. Round-robin polling preserves stale unresolved work without blocking later incidents.

Runtime evidence contains identifiers, release attribution, and bounded owned Rust stack frames. It excludes raw request bodies, user messages, breadcrumbs, credentials, and arbitrary fetch URLs. A source path missing from current main is recorded as held. Runtime evidence remains separate from CI failures and cannot substitute for a regression that fails at its intended assertion.

## Existing-test audit

The `test-audit` scope reads the historical queue in [`config/test-audit-backlog.json`](../../config/test-audit-backlog.json). Its 1,233 suite-qualified rows are the union of retained active cases and historical cases without an acceptance join. These cohorts overlap. The initial manifest has 1,183 pending rows and 50 explicit holds: 38 unsupported binary-target cases and 12 historically ignored or helper cases. It also records four historically paused cases whose identities were unavailable in the supplied evidence. The importer preserves that unresolved count instead of inventing queue entries. Historical catalogs, accepted-name counts and cursor movement grant no current execution credit.

Each page selects one exact test from an immutable main tree. Supported targets are `omg_lib` and root integration-test files. Missing or ambiguous source, unsupported targets, oversized files, ignored cases and native-only requirements stay held. A portable result cannot satisfy a native platform requirement.

The verifier distinguishes two observations:

| Purpose | Required actual executions | Result |
| --- | --- | --- |
| `existing-test-sensitivity` | Original test passes on intact source; the same test fails at its designated existing assertion on the controlled fault | Verified sensitivity to this particular fault. No patch is produced. |
| `existing-test-strengthening` | Old/intact passes; old/fault passes; stronger/fault fails at the added assertion; stronger/intact passes | A separately reviewable test strengthening. |

Strengthening preserves every original test byte and adds one assertion inside the selected function. A same-file fault must preserve the existing test section and its line positions. The controller restores the fault and publishes only the stronger test. Compiler failures, missing tests, setup failures, ignored cases and timeouts do not qualify as assertion failures. Each receipt binds the exact test, source blobs, fault, run attempt, compiler recipe and raw reports. The consumer refetches and reparses the compiler output, actual test catalog and execution logs.

These observations are narrower than test correctness. A detected fault proves sensitivity to that fault. A surviving fault can expose a gap, but it can also leave behavior unchanged. Fault plausibility and expected behavior still need review. This distinction follows the [cargo-mutants guidance on interpreting results](https://mutants.rs/using-results.html).

Audit source files are limited to 256 KiB each. The complete audit request and independent strengthening-review input are limited to 1 MiB. Normal repair collection keeps its 24,000-byte source limit and 64 KiB CI request limit. The trusted runner transports full audit bytes in at most 88 canonical base64 chunks of 16,000 characters. This avoids the Linux per-string process argument/environment limit documented in [execve(2)](https://www.man7.org/linux/man-pages/man2/execve.2.html). It does not increase model context or grant permission to omit source.

The coder rejects audit state above 1.5 MiB before persistence. Private review-record routes have their own 2 MiB cap. These application budgets are separate from the [SQLite Durable Object limit of 2 MB for a key and value together](https://developers.cloudflare.com/durable-objects/platform/limits/). An oversized result remains held.

Continuation binds the parent run, manifest digest, inventory digest and cursor. If main advances, it inventories the new source epoch without carrying over the old formatting result or execution credit. A completed sensitivity result or confirmed publication advances to the next row. A page that became stale before inference, or whose strengthening was not published, repeats the same row on the new source. An unpublished proof on unchanged main remains held; this path is not a general publication replay engine.

The configured six-hour recovery tick performs no model or test work itself. Its controller searches at most 500 recent manual `ai-review.yml` runs on main, across five pages of 100. It validates the original private record, pinned controller, manifest, exact workflow attempt and terminal publication job before dispatching a child. Dispatch deduplication checks up to 100 matching-source runs; known persisted duplicates stop before model or CI work. This bounded check does not guarantee exactly-once Actions dispatch. Missing records, controller drift and exhausted history remain explicit holds. Recovery does not restart an unknown campaign at zero or infer completion from missing history. This behavior requires the merged workflow and matching controller pins; source tests alone do not establish a running campaign.

The public `POST /sentry/events` endpoint accepts only a correctly signed event from the configured Sentry project. It verifies the HMAC against the original bounded body before parsing. Private evidence reads and acknowledgments require the existing verifier credential. An acknowledgment must name an existing durable review record containing the same event ID and body hash. The final coordinator acknowledges an event after publication succeeds or the durable review requires no publication. Duplicate delivery does not authorize duplicate repair work. See [Sentry webhook verification](https://docs.sentry.io/integrations/integration-platform/webhooks/) and [Workers Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/).

Sentry configuration uses `SENTRY_ORG_SLUG`, `SENTRY_PROJECT_SLUG`, `SENTRY_PROJECT_ID`, `SENTRY_ENVIRONMENT`, and secret `SENTRY_WEBHOOK_SECRET` on the OMG verifier Worker. Missing configuration disables public intake. The existing `OMG_SMOKE_SENTRY_DSN` belongs to smoke reporting and is not repurposed for application errors.

## Publication and independent approval

The publisher uses the dedicated `omg-ci-publisher` App, installed only on `omg-cli/omg`. Its short-lived token has Contents, Issues, and Pull requests write permissions. Only the trusted publisher receives that token. OpenCode receives no GitHub write credential. The official token action revokes the token in its post-job step. See [GitHub App workflow authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/making-authenticated-api-requests-with-a-github-app-in-a-github-actions-workflow).

Independent approval uses a different GitHub identity. It refetches the original private publication record, validates raw verifier objects and the entire published Git tree, and requires successful checks for the exact PR head. It admits QEMU artifacts through the existing inventory and source checks. It then requests an explicit patch verdict from a fresh DeepSeek review and binds the verdict to the base, head, tree, proposal, and complete patch. An insufficient-evidence verdict cannot become an approval. GitHub does not permit an author to approve its own PR. See [PR review rules](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request).

Approval targets an exact commit and does not merge or release it. Existing native, coverage, QEMU, assertion, and lint gates remain required. A new source-review finding is unconfirmed until the separate verifier admits its reproduction and repair.

An existing-test strengthening uses a separate publication and approval purpose. The publisher admits all four raw reports and the complete test-only tree. A fresh Inspector run receives the complete original and stronger test plus the private controlled fault. Its verdict is bound to the original audit digest and exact published head/tree. Sensitivity-only receipts cannot authorize publication. The fault and model review text are excluded from public approval text.

Publication retries at most three times within the same job, preserving its run attempt and idempotent issue/PR identities. Runtime polling can recover an unfinished canonical publication. A weekly page that exhausts publication retries stops; use **Re-run all jobs** for that run. **Re-run failed jobs** alone increments the attempt without recreating its successful earlier review record. This is an availability limit, not authorization to bypass a proof check.

The native SDK currently initializes only in the opt-in `omgd` daemon. Release builds default to Sentry environment `production`; debug builds default to `development` unless `SENTRY_ENVIRONMENT` is set. The intake allows the configured production environment. General CLI error capture and exact commit tagging need separate native implementation and verification. Do not claim those paths from a webhook fixture. See the [Rust SDK environment defaults](https://github.com/getsentry/sentry-rust/blob/0.49.0/sentry/src/defaults.rs).

### Script execution environments

The cloud script lane runs the unprivileged selection in `services/cloud-ci/runner/script-contracts.py`. Every discovered test has one declared execution lane. Eleven exact test IDs require the native host's elevated fixtures; the existing `Workflow checks` job still runs the full `make ci-workflow-quick` discovery, including those eleven. The cloud selection reports both lists, rejects duplicate identities, stale native assignments and empty portable selections, and never claims native acceptance. No test assertion or native/QEMU gate is removed.

Root-owned sticky `docs/` and `scripts/` directories allow temporary fixtures while keeping tracked files protected from candidate write, deletion, replacement and chmod. This uses the same ownership pattern as the existing workspace fixture directory. The image supplies genuine SSH and journalctl tools and configures only `/workspace` as a Git ownership exception; candidate sudo rights remain unchanged. See [sticky-directory behavior](https://man7.org/linux/man-pages/man2/unlink.2.html), [Git safe.directory](https://git-scm.com/docs/git-config), and the Debian [SSH](https://packages.debian.org/bookworm/amd64/openssh-client/filelist) and [journalctl](https://packages.debian.org/bookworm/amd64/systemd/filelist) package manifests.

A parallel check group settles before a failure receipt is written. Successful sibling execution and report evidence is retained even when another check fails; the overall receipt remains failed and later groups do not start.
